任务:$ARGUMENTS

## 1. 先自查,再问人

把所有未知项列出来,逐条分三类:

- **A 我自己能查** — 读代码、翻 git log、看已有实现和约定就能确认的。
  **全部自己查掉,一条都不许拿来问我。**
- **B 只有我知道** — 业务意图、优先级、取舍偏好、外部系统的现状、
  这次要不要顺带做某件事。只有这类才能问。
- **C 无所谓** — 有惯例或明显默认值的。自己定,记进假设,不要问。

## 2. 一次问完

B 类问题**一批问完,不要挤牙膏**。每个问题:

- 给 2–4 个具体选项,不要开放式问答
- 标出你的推荐项和推荐理由(我可能直接回"都用推荐的")
- 说清这个选择会导致什么不同的实现,选错的返工成本有多大

如果 B 类一条都没有,直接跳到第 3 步,不要为了走流程硬凑问题。

## 3. 输出 spec 并等我确认

```
目标:一句话说清做完是什么样
范围内:要做的事,逐条
明确不做:这次不碰的、容易被顺手扩进来的、我可能以为你会做但你不做的
假设:C 类自己定的默认值(我不反对就默认通过)
验收标准:怎么算做完 —— 具体到跑什么命令 / 截什么图 / 看什么输出
风险:哪一步最可能返工
```

## 退出条件

**不是"99% 置信度"**——那个你没法校准,别自评。
可以动手的唯一条件是:**B 类问题全部有答案,且 spec 我确认过。**

## 确认之后

进入自主推进模式:一口气做完,不再中途问我。
写的过程中冒出新歧义时:

- 自己能定的自己定,追加进 spec 的假设里,汇报时一并说
- 真正阻塞的(选错就白干)才回来问,并且同样一次问完
