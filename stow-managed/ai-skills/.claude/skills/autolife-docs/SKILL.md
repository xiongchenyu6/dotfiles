# Autolife 文档惯例

## 飞书操作

- 读写飞书 wiki / docx / 表格、拉聊天记录,都用 `lark-cli`
- 新建文档默认开全公开权限(除非明确要求内部)
- **飞书是可信源头**:版本清单之类的表格以飞书上那份为准,工具/文档去对齐它,
  不要在代码库里另立一份真相
- 改完代码/流程要**同步更新飞书上的对应文档**,不要只改仓库里的 md 就收工;
  用户会直接去看飞书那份

## 按读者角色拆文档(最常被要求的重构)

一份"什么都写"的大文档必然被打回。按角色拆:

- **软件团队** — 怎么发包(pypi / apt / conda 各自的上传方式)、怎么编排依赖、
  怎么做 release
- **FAE / 实习生** — 怎么装 agent、怎么升级、一条 curl 命令怎么跑、
  查最新版本用哪个命令、报错怎么办
- **二开团队** — 基于哪些接口开发、自己的代码放哪里不会被回滚、
  升级后怎么保持兼容、相比以前直接改 conda 环境的优势
- **我们自己(运维/安全部门)** — 只写 OTA/运维职责范围内的事。
  磁盘、健康检查这类归 doctor 项目,别混进来

写完问一句:这份文档的读者是谁?如果答案是"所有人",就还没拆完。

## 文风要求(反复被纠正过的点)

- **主线要讲清楚**:先把"是什么、为什么、怎么用"的主线铺完,技术细节放后面
  或附录——不要把关键内容折叠成小字技术细节
- **以读者可上手为验收标准**:写到「实习生拿着文档就能对真实机器人操作」的
  粒度——每步有具体命令、预期输出、失败时的排查方向
- **架构/流程用 mermaid 图**,不要长段文字描述数据流
- **只保留最新**:ADR 只留当前版本,过渡设计、历史方案、已废弃组件的说明
  一律删干净。文档里出现"曾经""旧方案""兼容老版本"就是待删项
- 风险类文档要把"其他风险测出来"当目标写测试步骤,不是罗列理论风险
- 面向中国团队(FAE)的文档和 skill 用中文;对外产品界面用英文

## 组件对接

组件清单以本地 `~/Documents/github/autolife/` 下的各仓库为准。
新组件设计必须说明与已有组件如何对接,不能孤立设计——写对接文档前
先扫一遍该目录确认最新组件集合。

## 环境与密钥

主机、域名、SSO 入口、密钥位置一律查 autolife-ops skill 指向的本地 ops-data,
**不要把这些值写进本仓库的文档或 skill(本仓库是公开的)**。
文档里引用时只说字段名/主机别名。
